# 5버전 커스텀 화면 구현 방식

## 1. 머리말

### 1.1 이 문서는 무엇인가

Zabbix 5.0 위에 만들어져 있던 커스텀 화면이 **어떤 데이터를, 어떻게 가져와서, 무엇을 기준으로 판정했는지**를 화면별로 정리한 참고 문서다.
7버전 모듈을 만들거나 고칠 때 "5버전에서는 원래 어떻게 했나"를 찾아보는 용도다.

### 1.2 읽는 법

- 2장은 모든 화면이 같이 쓰는 구조다. 먼저 읽는다.
- 3장은 화면마다 같은 소제목(화면 / 데이터 출처 / 조회 방법 / 판정 기준 / 근거 / 확실하지 않은 것·없는 것 / 알려진 문제)으로 되어 있다.
- 4장은 코드에 이름만 나오고 내용을 받지 못한 파일 목록이다.
- 근거는 `파일명:줄` 로 적는다. 예) `CControllerLowserver.php:102`. 화면 설명이 근거면 "5버전 화면에서 확인"이라고 적는다.
- 증거에 없는 내용은 "확인 못 함"이라고 적는다. 추측은 넣지 않았다.

### 1.3 근거가 얼마나 확실한가

- 5버전 소스는 **일부만 복원된 것**이다. 파일 전체가 있는 것도 있고, 앞이나 뒤가 빠진 것도 있고, 이름만 아는 것도 있다.
- **줄 번호는 복원본 기준**이다. 앞부분이 빠진 파일은 빠진 구간을 한 줄로 표시했기 때문에 원본 줄 번호와 다르다.
- 복원본 안의 표시: `[GAP ...]` = 받지 못한 구간, `⟦?⟧` 또는 `[불명]` = 읽지 못한 글자, `[a|b?]` = 두 가지로 읽히는 글자.
- 들여쓰기, 빈 줄 수, 작은 구두점(따옴표, 쉼표, 괄호 종류)은 복원 과정에서 틀렸을 수 있다.
- 화면 설명(버튼, 필터, 열 이름, 값 모양)은 5버전 화면에서 확인한 것이다. 화면 일부가 가려져 못 읽은 곳이 있다.

### 1.4 이름 표기 규칙

5버전 커스텀 클래스와 파일 이름에는 회사 이름이 접두어로 붙어 있다. 이 문서는 공개 저장소에 들어가므로 접두어를 `...` 으로 바꿔 적는다.

| 이 문서의 표기 | 뜻 |
|---|---|
| 기본 트레잇(`C...`), 파일은 `C....php` | 접두어만으로 된 이름의 공통 트레잇 |
| `...Filter`, `...Itms`, `...Middle`, `...Key`, `...Data` | 공통 트레잇·클래스 |

## 2. 공통 구조

### 2.1 routing.php

커스텀 화면은 `routing.php` 한 파일에 "액션 이름 → [컨트롤러 클래스, 레이아웃, 뷰]" 로 등록되어 있다.

```php
'lowserver' => ['CControllerLowserver', 'layout.htmlpage', 'report/lowserver'],
'popup.topcpu'=>['CControllerPopupTopCpu','layout.json','report/popup.topcpu'],
'lowserver.view.csv'=>['CControllerLowserverCSV','layout.csv','server.view.csv'],
'lowserver.php' => ['CLegacyAction', null, null],
```

| 레이아웃 | 쓰임 |
|---|---|
| `layout.htmlpage` | 일반 화면 |
| `layout.json` | 팝업 (뷰가 JSON 을 출력) |
| `layout.csv` | CSV 내려받기 |
| `layout.widget` | 위젯 (`widget.data.analysis.svggraph.view` 한 건) |
| `CLegacyAction`, null, null | `xxx.php` 형태의 옛 방식 페이지 이름 등록 |

- 화면마다 `xxx.php` (레거시), `xxx` (화면), `xxx.view.csv` (CSV), `popup.xxx` (팝업) 을 묶어 등록하는 모양이다.
- `windowsall`, `windowsall.view.csv` 위에는 `//# 임시 라우터` 주석이 있다.
- `perf.analysis.view`, `perf.analysis.check`, `popup.perf.analysis` 는 이 파일에 없다. 어디에 등록했는지 확인 못 함.
- 이 파일을 Zabbix 코어가 어떻게 읽어 들이는지는 복원본에 없다. 확인 못 함.

근거: `routing.php:8-63`

### 2.2 컨트롤러의 공통 모양

커스텀 컨트롤러(SW 인벤토리, 저사용, 일일점검, 윈도우즈)는 거의 같은 순서로 되어 있다.

1. `init()` 에서 `$this->disableSIDValidation();`
2. `checkInput()` 에서 레거시 방식 `check_fields($fields);` 를 부르고 무조건 `return true;`
3. `checkPermissions()` 는 무조건 `return true;`
4. `doAction()` 에서
   1. 규칙 파일(JSON)을 읽는다.
   2. 필터 값을 프로파일에 저장하고 다시 읽는다.
   3. `API::Host()->get()` 으로 호스트 목록을 가져온다.
   4. 트레잇의 함수로 줄마다 값을 덧붙인다(가운데 처리).
   5. 글자 필터를 적용한다.
   6. 정렬하고 페이지를 나눈다.
   7. `tableBody()` 로 줄마다 화면에 낼 값 배열을 만든다.
   8. `CControllerResponseData` 로 뷰에 넘긴다.

근거: `CControllerLowserver.php:16-150`, `CControllerWindows.php:16-251`, `CControllerSwinventories.php:17-69`

### 2.3 공통 트레잇과 클래스

| 이름 | 종류 | 하는 일 | 복원 |
|---|---|---|---|
| 기본 트레잇(`C...`) | trait | 값 출력 도우미(`outputValues`, `ellipsis`, `printListKey`), 표 줄 만들기(`tableBody`, `tableBody2`), 테이블 있는지 검사(`isTable`) | 전체 |
| `...Filter` | trait | 글자 필터(`isFilter`, `filtering`, `stringInFilter`) | 전체 |
| `...Itms` | trait | ITSM 표 조회(`itsm_hostList`, `itsm_description`) | 전체 |
| `...Middle` | class | 규칙 파일의 `middleware.before` 에 적힌 함수를 차례로 실행 | 전체 |
| `...Key` | class | 화면에서 쓰는 아이템 키 목록 | 전체 |
| `CDataItems` | class | `zabbix.items` 에서 키로 아이템을 찾는 조회 도우미 | 앞 2줄 빼고 전체 |
| `...Data` | trait | 거의 모든 컨트롤러와 `...CPU`, `...Memory` 가 `use` 한다. 내용 없음 | **없음** |
| `CDataValue` | class | `...HostBox` 가 `new` 한다. 내용 없음 | **없음** |

#### 기본 트레잇(`C...`)

- `outputValues($value, $max=20)` : 문자열 길이(`strlen`)가 20 을 넘으면 앞 20글자만 보이고 전체 값은 힌트(마우스를 올리면 뜨는 상자)로 넣는다. 자르는 함수는 `iconv_substr($str,0,$max,"utf-8")` 이고 `...` 표시는 붙이지 않는다. 배열이면 첫 값만 보이고, 값이 2개 이상이면 힌트 표를 붙인다. 이 힌트 표에는 `if($cnt < 1)` 조건 때문에 첫 줄만 들어간다.
- `tableBody($rule, $data)` : 규칙 파일의 `table.func` 가 **이름 배열**일 때 쓴다. 이름마다 `$this->$func($data)` 를 불러 한 줄을 만든다. 그 이름의 함수가 없으면 글자 `"func"` 가 들어간다.
- `tableBody2($rule, $data)` : `table.func` 가 **이름 → 매개변수 객체**일 때 쓴다. `$this->$func($data, $params)` 를 부른다. 함수가 없으면 `"funcc"` 가 들어간다.
- `isTable($schema, $table)` : `information_schema.tables` 로 테이블이 있는지 본다. PostgreSQL 의 `exists` 결과가 `"f"` 인지로 판단한다.

근거: `C....php:18-22`, `C....php:27-73`, `C....php:99-122`, `C....php:124-141`

#### `...Filter`

- `isFilter($key)` : `$this->filter[$key]` 가 있고 비어 있지 않으면 참.
- `filtering($key, $field, $rowdatas)` : 필터 값과 줄의 `$field` 값을 둘 다 소문자로 바꿔 **부분 일치**(`strpos`)로 비교한다.
  - 줄에 그 필드가 없으면 줄을 지운다.
  - 값이 객체(예: 빨간 `-` 표시)면 줄을 지운다.
  - 값이 배열이면 원소 중 하나라도 일치하지 않으면 줄을 지운다.

근거: `...Filter.php:11-17`, `...Filter.php:19-50`, `...Filter.php:52-60`

#### `...Itms` (ITSM 표)

- 표 이름은 `itsm_info`, 스키마 이름은 소스에 고정 문자열로 적혀 있다(마지막 글자 판독이 확실하지 않아 여기에 적지 않는다).
- `itsm_hostList()` : `SELECT id, ci_name, ip_address, description` 으로 표 전체를 읽는다. 표가 없으면 빈 배열.
- `itsm_description($host)` : `where ci_name ilike '<호스트 표시 이름>'` 으로 한 줄을 찾는다. 있으면 그 줄을 돌려주고, 없으면 빨간 `-` 와 "ITSM 데이터가 없습니다" 힌트를 돌려준다. 표 자체가 없으면 "ITSM 테이블이 없습니다" 힌트.
- 이 함수는 호출될 때마다 `isTable` 조회 1번 + 본 조회 1번을 한다.

근거: `...Itms.php:9-11`, `...Itms.php:29-42`, `...Itms.php:45-76`

#### `...Middle` (가운데 처리)

```php
$before = $this->App->rules->middleware->before;
foreach($before as  $func => $params) {
    if(method_exists($this->App, $func)){
        $this->App->$func($params);
    }
}
```

규칙 파일의 `middleware.before` 에 적힌 순서대로 컨트롤러(트레잇 포함)의 함수를 부른다. 없는 함수는 조용히 건너뛴다.
복원본에서 이 클래스를 쓰는 곳은 SW 인벤토리 하나다. 저사용·윈도우즈·일일점검은 컨트롤러가 함수를 직접 부른다.

근거: `...Middle.php:16-24`, `CControllerSwinventories.php:238-240`

### 2.4 JSON 규칙 파일

위치는 `./autoever/conf/rules/<이름>.json` 이다. 컨트롤러가 `json_decode(file_get_contents(...))` 로 읽는다.

```json
{
    "title":"고사용 서버 사용현황",
    "table":{
        "thead":[ {"title":"호스트","sort":"name"}, "IP", "description",
                  {"title":"평균CPU사용율(%)","sort":"_cpuavg"}, "Peak(%)" ],
        "func":[ "host_name", "host_ip", "host_description", "server_cpu", "server_peak" ]
    }
}
```

### 2.8 팝업 호출 방식

1. 화면 쪽에서 `PopUp("<액션>", {매개변수}, null, this)` 를 부르는 링크를 만든다.


  | 열 제목 | 정렬 필드 | 값을 만드는 함수 | 읽는 필드 |

  | 호스트 | `name` | `host_name` | `name` |

  | IP | 없음 | `host_ip` | `ip` |
  | Description | 없음 | `host_description` | `description` |
  | OS | `_osname` | `host_os` | `osname` |
  | WEB | `_web` | `host_web` | `web` |
  | WAS | `_was` | `host_was` | `was` |
  | DB | `_db` | `host_db` | `db` |
  | 이중화 솔루션 | 없음 | `host_duplex` | `duplex` |
  | Agent설치 | `_agent` | `host_agent` | `agent` |

**데이터 출처**

| 무엇 | 어디서 |
|---|---|
| 줄의 바탕(호스트, IP, Description) | ITSM 표 `itsm_info` 의 `id, ci_name, ip_address, description` |
| Zabbix 호스트와의 연결 | `API::Host()->get(['output' => ['hostid','name','host'], 'groupids' => ..., 'preservekeys' => true])` |
| OS, WEB, WAS, DB, 이중화 | `zabbix.host_inventory` 의 `os`, `software_app_a`, `software_app_b`, `software_app_c`, `software_app_d` |
| OS·버전·WEB·WAS·DB·이중화 아이템 | `zabbix.items` 에서 `...Key` 의 키로 itemid 만 찾는다. **값은 읽지 않는다**(아래 판정 기준) |
| Agent 미설치/예외 상태 | 별도 표 `extends_agent` (`hostid, agent, explanation, clock, userid, username, useralias`) |
| 필터 값 | 프로파일 `web.swinventory.filter.*` |

**조회 방법**

1. `swinventory.json` 을 읽는다.
2. 필터를 프로파일에 저장/삭제하고 다시 읽는다.
3. `적용` 을 누른 것도 아니고 `page` 요청도 아니면 Agent 체크 3개를 모두 `"1"` 로 만들고 프로파일에도 `"1"` 을 쓴다.
4. 그룹·호스트 필터로 Zabbix 호스트를 가져온다.
5. `itsm_hostList()` 로 ITSM 표 전체를 읽는다.
6. ITSM 줄마다 Zabbix 호스트를 돌면서 `strtolower($host['host']) == strtolower($row['ci_name'])` 이면 그 호스트의 hostid 를 줄의 키로 쓴다. 맞는 호스트가 없으면 키는 `"itsm_".$row['id']` 다.
7. 줄을 만든다: `hostid`, `host`(Zabbix 표시 이름), `name`(ITSM `ci_name`), `ip`(ITSM), `description`(ITSM), `itsm`(ITSM id).
8. `...Middle` 이 `middleware.before` 의 함수를 순서대로 부른다: `middle_agent` → `middle_osName` → `middle_web` → `middle_was` → `middle_version` → `middle_db` → `middle_duplex` → `middle_inventory`.
9. 글자 필터 6개를 차례로 적용한다 (`filter_os`→`osname`, `filter_web`→`web`, `filter_was`→`was`, `filter_db`→`db`, `filter_duplex`→`duplex`, `filter_itms`→`name`).
10. Agent 체크 3개로 비트 값 `$mask` 를 만든다(설치 1, 미설치 +2, 예외 +4).
11. 이후(마스크로 줄 거르기, 정렬, 페이지 나누기, 표 만들기)는 복원본에 없다.

**판정 기준**

- **줄의 기준은 ITSM 표다.** Zabbix 에만 있고 ITSM 에 없는 호스트는 줄이 생기지 않는다. ITSM 에만 있는 장비는 `itsm_<id>` 키로 줄이 생긴다.
- **호스트 연결**: Zabbix 의 `host`(기술 이름)와 ITSM 의 `ci_name` 을 소문자로 바꿔 **완전 일치** 비교.
- **Agent 상태** (`...HostAgent`):

  | 조건 | 표시 | 내부 값 |
  |---|---|---|
  | ITSM 줄과 Zabbix 호스트가 연결됨(hostid 가 숫자) | `설치` (글자만) | 1 |
  | 연결 안 됨, `extends_agent` 의 최신 줄(`order by clock desc`)의 `agent` 가 2 | `미설치` (링크) | 2 |
  | 위와 같고 `agent` 가 4 | `예외` (링크) | 4 |
  | 위와 같고 `agent` 가 그 밖의 값 | `설치` | 그 값 |
  | `extends_agent` 에 줄이 없음 | `미설치` (링크) | 2 |
  | 조회 실패 | `조회오류` | 2 |

- **OS / WEB / WAS / DB / 이중화 값**: 실제로 화면에 나오는 값은 `host_inventory` 의 값이다. 순서는 이렇다.
  1. `middle_osName` 등이 `DBExtend()` 를 부른다. `DBExtend()` 는 키로 itemid 를 찾지만, 이력 값을 읽는 쿼리가 주석 처리되어 있어 `$trends` 가 항상 비어 있다. 그래서 아이템이 있는 호스트는 빨간 `--`("데이터가 없습니다" 힌트), 아이템이 없는 호스트는 빨간 `-`("item 정보가 없습니다" 힌트)가 들어간다.
  2. 마지막에 실행되는 `middle_inventory` 가 `host_inventory` 에 값이 **비어 있지 않은** 항목만 덮어쓴다 (`os` → `osname`, `software_app_a` → `web`, `software_app_b` → `was`, `software_app_c` → `db`, `software_app_d` → `duplex`).
  3. 따라서 인벤토리 값이 없는 칸은 빨간 `--` 또는 `-` 로 남는다.
- **글자 필터**: 소문자 부분 일치. 값이 객체(빨간 `-`, `--`)인 줄과 필드가 없는 줄은 지워진다(2.3 `...Filter`).
- **긴 값**: 20 을 넘으면 잘라서 보이고 전체는 힌트.
- **기본 필터**: Agent 설치·미설치·예외 모두 체크.
- **정렬 허용 값**: `name, osname, _osname, _web, _was, _db, agent, _agent, db, duplex`. 기본 정렬은 복원본에 없다.

## 3.3 저사용 서버

**화면** (5버전 화면에서 확인)

- 액션: `lowserver`. CSV `lowserver.view.csv`, 팝업 `popup.lowserver`.
- 메뉴 위치: 보고서 > 저사용 서버 사용현황.
- 제목: `저사용 서버 사용현황`. 브라우저 탭 제목은 `Low Server`.
- 필터: 호스트 그룹, 호스트, 시작(날짜), 종료(날짜), 안내 글 `※최대 1년까지 기간 지정이 가능합니다.`, 시간 라디오 3개(`업무시간 사용현황(09시~18시)` / `업무외시간 사용현황(18시~09시)` / `전체사용현황`). 버튼 `적용`, `리셋`.
- 표 위 빨간 글: `※저사용 기준: 평균사용률 30% 미만 / Peak 70% 미만`.
- 표의 열: 호스트 / IP / description / 평균CPU사용률(%) / Peak(%).
- 값 모양: 소수 둘째 자리 + `%` (예: `2.29%`). description 은 20글자쯤에서 잘린다.
- 버튼: `CSV 내보내기`, `기준설정`.
- 팝업: `기준설정` 을 누르면 `수집기준 설정` 창이 뜬다. 입력 4개 — 저사용 평균 CPU 사용률(%) `30` %미만, 저사용 Peak기준 `70` %미만, 고사용 평균 CPU 사용률(%) `50` %이상, 고사용 Peak기준 `70` %이상. 안내 글 `1~99 사이의 숫자만 입력해 주세요`, `모든 항목은 필수입력값입니다`. 버튼 `설정`, `취소`.

**데이터 출처**

| 무엇 | 어디서 |
|---|---|
| 호스트 | `API::Host()->get(['output' => ['hostid','name'], 'groupids' => ..., 'preservekeys' => true])` |
| CPU 평균·최대 | 별도 표 `zabbix.extends_trends_day` (하루에 아이템당 한 줄. 3.13 참고) |
| CPU 아이템 키 | `...Key::serverCpuUsage()` 의 3개 키 |
| IP | `API::HostInterface()->get(['hostids' => $id])` 의 첫 번째 `ip` |
| description | ITSM 표 `itsm_info.description` (`ci_name ilike 호스트 표시 이름`) |
| 저사용 기준 값 | 프로파일 `web.report.server.cpulow`, `web.report.server.peaklow` |
| 필터 값 | 프로파일 `web.lowserver.filter.*` |

**조회 방법**

1. `lowserver.json` 을 읽는다.
2. `setProfiles()` 로 필터를 저장/삭제, `setFilters()` 로 읽는다.
3. 그룹·호스트 필터로 호스트를 가져온다.
4. `...CPU` 객체를 만들고 기간과 시간 구분을 넘긴다.
   ```php
   $serverCPU = new ...CPU(zbx_objectValues($this->rows, 'hostid'));
   if(isset($this->data['from'])) $serverCPU->from($this->data['from']);
   if(isset($this->data['to'])) $serverCPU->to($this->data['to']);
   $serverCPU->process( $this->data['worktime'] ); // 업무시간에 맞는 데이터 조회
   ```
   (위 인용의 클래스 이름만 `...` 으로 바꿨다.)
5. `process()` 는 `extends_trends_day` 를 **아이템별로 묶어** 읽는다.
   ```php
   $query = "SELECT max(hostid) as hostid, itemid, sum(num)";
   $query .= " ,min(work_min) as work_min, avg(work_avg) as work_avg, max(value_max) as work_max";
   $query .= " FROM zabbix.".$tablename;
   $query .= " where clock >= ".$this->from;
   $query .= " and clock < ".$this->to;
   $query .= " and ".$this->queryWhereLikeOr($keyname);
   $query .= " and weekend in (1,2,3,4,5)"; //토, 일요일은 제외
   $query .= " group by itemid;";
   ```
   - 시간 구분이 `"work"` 이면 위 쿼리(`query_Work`)를 쓴다.
   - 그 밖(`"night"`, 전체, 값 없음)이면 `query_all` 을 쓴다. `value_*`, `work_*`, `night_*` 를 모두 읽고 요일 조건이 없다.
6. 호스트마다 `$serverCPU->get($hostid)` 로 값을 꺼내 기준과 비교한다. 기준에 맞지 않거나 값이 없는 호스트는 목록에서 뺀다.
7. `pagenation()` 으로 정렬하고 페이지를 나눈다.
8. `tableBody()` 로 줄을 만든다. 평균과 Peak 은 `sprintf("%0.2f", $value)."%"` 로 찍는다.

**판정 기준**

- **기본 기간**: 시작 = `date("Y-m-d", strtotime("first day of -1 month"))`, 종료 = `date("Y-m-d", strtotime("last day of -1 month"))`. 즉 **지난달 1일 ~ 지난달 말일**.
- **기간을 시각으로 바꾸는 법**: 시작일 `00:00:00`, 종료일 `23:59:59`. 쿼리 조건은 `clock >= 시작` 그리고 `clock < 종료`.
- **시간 구분과 쓰는 값**:

  | `worktime` 값 | 읽는 쿼리 | 평균 | Peak | 요일 |
  |---|---|---|---|---|
  | `"work"` | `query_Work` | `avg(work_avg)` | `max(value_max)` 을 `work_max` 라는 이름으로 읽음 | 월~금만 (`weekend in (1,2,3,4,5)`) |
  | `"night"` | `query_all` | `avg(night_avg)` | `max(night_max)` | 모든 요일 |
  | 그 밖, 또는 값 없음 | `query_all` | `avg(value_avg)` | `max(value_max)` | 모든 요일 |

- **업무시간 구간**(집계 표를 만들 때): 09:00 이상 18:00 미만. 업무외 = 00:00~09:00 과 18:00~23:59:59. 자세한 것은 3.13.
- **저사용 판정식**:
  ```php
  if($avg > $cpulow || $max > $cpupeak) {
      //기준조건 불일치
      unset($this->rows[$hostid]);
      continue;
  }
  ```
  평균이 기준 **초과**이거나 Peak 이 기준 **초과**이면 뺀다. 남는 것은 `평균 <= 평균 기준` **그리고** `Peak <= Peak 기준` 인 호스트다.
- **기준 기본값**: Peak 기준은 프로파일 값이 없으면 `70`. 평균 기준은 프로파일 값이 없으면 `30` 또는 `20` (복원본에서 두 가지로 읽힌다. 화면의 기준 글과 설정 창은 `30` 이다).
- **집계 값이 없는 호스트**: 목록에서 뺀다(`// no-trend delete`).
- **한 호스트에 CPU 아이템이 여러 개일 때**: `get()` 이 `$this->rows[$hostid][0]` 만 돌려주므로 첫 번째 아이템의 값만 쓴다.
- **정렬**: 허용 값 `name, cpuavg, _cpuavg`. 기본 `name` 오름차순.
- **기간 제한**: "최대 1년" 안내 글은 화면에 있으나, 컨트롤러에 1년을 넘는지 검사하는 코드는 없다(`validateTimeSelectorPeriod()` 호출이 있으나 그 함수의 내용은 복원본에 없다).

**근거**

- 규칙 파일 읽기: `CControllerLowserver.php:57`

**조회 방법 — 일일점검 표**

1. `daily.json` 을 읽는다.
2. 조회 기간을 정한다(아래 판정 기준).
3. 모든 호스트를 가져온다: `API::Host()->get(['output' => ['hostid','name'], 'preservekeys' => true])`. (이 결과는 표 계산에 쓰이지 않는다.)
4. 항목별 함수 7개를 차례로 부른다: `middle_OS`, `middle_Work`, `middle_Disk`, `middle_Disk30`, `middle_CPU`, `middle_Paging`, `middle_Duplex`.
5. 각 함수는 똑같이 세 가지를 계산한다.
   ```php
   $this->problems_os_host = $this->isTagEventHosts($this->tag_os['name'], $this->tag_os['value']);
   $this->problems_os = count($this->problems_os_host);
   $this->total_os = count($this->totalTagHost($this->tag_os['name'], $this->tag_os['value']));
   $this->operation_os = $this->total_os - $this->problems_os;
   ```
6. `totalTagHost()` (점검대상):
   ```sql
   SELECT hostid, count(itemid) as item_num FROM items
    where itemid in (SELECT itemid FROM functions
      where triggerid in (select triggerid from trigger_tag where tag='REPORTS' and value='<태그 값>'))
    group by hostid
   ```
   나온 hostid 를 `API::Host()->get()` 에 넣어 돌아온 호스트 수를 센다.
7. `isTagEventHosts()` (장애발생 호스트): 위와 같되 트리거를 "기간 안에 장애 이벤트가 있는 것"으로 좁힌다.
   ```sql
   select objectid as triggerid from events
    where source = 0 and objectid in (<태그가 붙은 triggerid>)
    and value = 1
    and clock >= <from> and clock < <to>
    group by objectid
   ```
8. 규칙 파일의 `table.data` 를 돌면서 줄을 만든다. 이름이 컨트롤러의 함수이면 실행한 결과를, 아니면 그 글자를 그대로 넣는다.
   ```php
   foreach ($data['rules']->table->data as $key => $row) {
       foreach($row as $func) {
           if(method_exists($this, $func)){
               $data['rows'][$key] []= $this->$func();
           } else {
               $data['rows'][$key] []= $func;
           }
       }
   }
   ```
9. 장애 칸: 수가 0 보다 크면 `CSpan` 에 링크 모양 클래스(`ZBX_STYLE_BTN_LINK`)를 주고 `setHint()` 로 호스트 표를 붙인다. 0 이면 숫자만 낸다.
10. 호스트 표(`hostTables`)의 각 호스트 이름은 기본 장애 화면으로 가는 링크다: `action=problem.view`, `filter_hostids[]=<hostid>`, `filter_tags[0][tag]=REPORTS`, `filter_tags[0][value]=<태그 값>`, `filter_show=2`, `from=now-5d`, `to=now`.

**조회 방법 — Top 10 팝업**

1. 모든 호스트를 가져온다 (`output` 은 `hostid`, `name`).
2. 어제 날짜를 구한다: `$today = date("Y-m-d", strtotime("-1 day"));` (변수 이름은 `$today` 지만 값은 어제다).
3. CPU: `new ...CPU(hostid 목록)` → `from($today)->to($today)` → `process()`. 시간 구분을 넘기지 않으므로 `query_all` 을 쓴다.
   Memory: `new ...Memory(hostid 목록)` → 같은 순서. `...Memory::process()` 는 먼저 `check()` 를 불러 집계 표를 점검·보충한 뒤 읽는다.
4. 호스트마다 IP, Description 을 붙이고, 평균을 `sprintf("%0.2f", $cpu['value_avg'])` 로 넣는다. 값이 없으면 0.
5. `order_result($this->hosts, "cpuavg", ZBX_SORT_DOWN);`
6. 앞에서부터 10줄만 번호(`num`)를 붙여 담는다.
7. 뷰가 표를 만들어 JSON 으로 낸다.

**판정 기준**

- **조회 기간**:
  ```php
  //기간선택 없음 : 작일07:00 ~ 당일06:59
  $today = date("Y-m-d",time());
  $data['to'] =  strtotime($today." 06:59:59");
  $data['from'] = $data['to'] - 86399;
  ```
  기본은 **어제 07:00:00 ~ 오늘 06:59:59**. 요청에 `period1` 이 있으면 양쪽에서 하루(86400초)를 빼고(D-1), `period2` 가 있으면 이틀을 뺀다(D-2). 값은 보지 않고 **있는지만** 본다. 둘 다 있으면 `period1` 이 먼저다.
- **이벤트 조건**: `clock >= from` 그리고 `clock < to`. 따라서 06:59:59 정각의 이벤트는 빠진다.
- **점검대상**: 해당 태그 값이 붙은 트리거에 연결된 아이템을 가진 호스트 수. 전체 호스트 수가 아니다.
- **장애발생 호스트**: 위 트리거 중, 조회 기간 안에 **장애 발생 이벤트(`value = 1`)가 새로 생긴** 트리거에 연결된 호스트 수. 기간 전에 발생해 아직 풀리지 않은 장애는 세지 않는다.
- **정상호스트** = 점검대상 − 장애발생 호스트.
- **"90% 초과", "30% 급증", "20% 급증", "1%" 같은 숫자**: 컨트롤러와 트레잇에는 이 숫자를 비교하는 실행 코드가 없다. 판정은 태그가 붙은 **트리거**가 하고, 화면은 그 이벤트를 셀 뿐이다. 트리거 식은 복원본에 없다.

## 3.7 윈도우즈 패치 현황 (+ 상세 팝업, 윈도우 전체)

**화면** (5버전 화면에서 확인)

- 액션: `windows`. CSV `windows.view.csv`, 팝업 `popup.windows`.
- "윈도우 전체": `windowsall`, `windowsall.view.csv`, `popup.windows.all`. routing.php 에 `임시 라우터` 라고 적혀 있다. 화면 설명은 없다.
- 메뉴 위치: 보고서 > 윈도우즈 패치 현황.
- 제목: `Windows Patch현황`.
- 필터: 호스트 그룹, 호스트, HotFix ID(글자), 수집월선택(날짜, 예 `2026-10-01`). 버튼 `적용`, `리셋`.
- 표의 열: 호스트(정렬 표시) / IP / description / Patch File명.
- 값: description 은 20글자쯤에서 잘린다. `Patch File명` 칸은 모든 줄이 `상세보기` 링크였다.
- 버튼: `CSV 내보내기`.
- 팝업 `Windows 패치 상세정보`: 열 10개 — Caption / CSName / Description / FixComments / HotFixID / InstallDate / InstalledBy / InstalledOn / Name / ServicePackInEffect. 날짜 모양 `M/D/YYYY`. Description 값은 `Security_Update`, `Update` 처럼 빈칸이 밑줄로 바뀌어 있다. 아래 버튼 `닫기`.

**데이터 출처**

| 무엇 | 어디서 |
|---|---|
| 호스트 | `API::Host()->get(['output' => ['hostid','name'], 'groupids' => ..., 'preservekeys' => true])` |
| 윈도우즈 여부 | `zabbix.host_inventory` 의 `os` |
| 패치 목록 아이템 | `zabbix.items` 에서 키 `vfs.file.contents[C:\Program Files\zabbix\script\Result\Win_Update_All.txt,ANSI]` |
| 패치 목록 내용 | `zabbix.history_text` 의 `value` (그 달의 값) |
| IP | `API::HostInterface()->get(['hostids' => $id])` 의 첫 번째 `ip` |
| description | ITSM 표 `itsm_info.description` |
| 필터 값 | 프로파일 `web.windows.filter.*` |

**조회 방법 — 목록**

1. `windows.json` 을 읽는다.
2. 필터를 저장/삭제하고 읽는다. 수집월(`from`)이 없으면 지난달 1일.
3. 그룹·호스트 필터로 호스트를 가져온다.
4. 윈도우즈만 남긴다.
   ```php
   $query = "SELECT hostid, os FROM zabbix.host_inventory where os ilike ('%windows%');";
   ```
   이 결과에 없는 호스트는 목록에서 뺀다.
5. `middle_patchFile()`, `middle_patchVersion()`, `middle_patchDate()` 를 차례로 부른다.
6. `middle_patchDate()`:
   1. 그 달의 범위를 구한다: 시작 = `strtotime($this->from)`, 끝 = 그 달 말일 `23:59:59`.
   2. `CDataItems` 의 `fetchOr()` 로 키가 **정확히 같은** 아이템을 찾는다(호스트당 1건).
   3. `SELECT * FROM zabbix.history_text where itemid in (...) and clock >= 시작 and clock < 끝` 으로 값을 모두 읽는다.
   4. 호스트마다: 아이템이 있으면 `itemid` 를 줄에 넣고, 값이 있으면 `patch` = 읽은 값 중 첫 번째, 없으면 `patch` = `"-"`.
7. HotFix ID 필터가 있으면 `filtering("hotfixid", 'patch', $rowdatas)` 로 거른다.
8. 정렬, 페이지 나누기, `tableBody()`.

**조회 방법 — 상세 팝업**

1. 링크가 `PopUp("popup.windows", {"hostid":..., "itemid":..., "from":...}, null, this)` 를 부른다.
2. 컨트롤러가 그 달 범위를 다시 계산하고 한 줄을 읽는다.
   ```php
   $query = "SELECT * FROM zabbix.history_text where itemid in (".$itemid.") ";
   $query .= " and clock >=".$from." and clock <".$to;
   $query .= " and value <> ''";
   $query .= " order by clock desc limit 1";
   ```
3. 뷰의 `wmic_qfe_parser()` 가 글자를 표로 바꾼다.
   1. 줄바꿈으로 나눈다.
   2. 빈칸을 모두 `_` 로 바꾼다.
   3. 긴 `_` 묶음(약 15개)을 "빈 칸" 표시 `*****` 로 바꾸고, `_` 2개 이상을 열 구분으로 본다.
   4. 첫 줄을 열 제목으로 쓴다.
   5. 둘째 줄부터 값을 넣는다. 값이 없거나 `*****` 이면 빈칸 한 글자.
   6. `order_result($info, "InstalledOn", "desc")` 로 정렬해 표에 넣는다.

**조회 방법 — 윈도우 전체** (`windowsall`)

**판정 기준**

- **팝업에 보이는 값**: 그 달에 수집된 값 중 **가장 최근 것 1건**(빈 값 제외).
- **팝업 정렬**: `InstalledOn` 글자 기준 내림차순. 날짜가 `M/D/YYYY` 글자라서 날짜 순서와 같지 않다.
- **정렬**: 허용 값 `name, patchfile, patch`. 기본 `name` 오름차순.

**조회 방법 — CSV**

1. 뷰 맨 아래에 숨은 폼이 있다: `<form action="./zabbix.php?action=data.analysis.csv" method="post" id="excelDownloadForm">` 안에 `jsonStr` 입력 하나.
2. 컨트롤러가 `$_POST['jsonStr']` 을 `json_decode` 한다.
3. 데이터 셋마다 (호스트나 아이템이 비어 있으면 건너뜀) 아이템을 찾는다.
   ```php
   $sql = "SELECT h.host, i.name, i.itemid, i.units, i.value_type from items as i
       INNER JOIN hosts as h
       ON i.hostid = h.hostid
       WHERE h.host IN ('".implode("','", $jsonData[$i]['hosts'])."')
       AND i.name IN ('".implode("','", $jsonData[$i]['items'])."')";
   ```
4. 아이템마다 기간 길이에 따라 표를 고른다(아래 판정 기준).
5. `SELECT * from <표> WHERE itemid = <itemid> AND clock >= <time_from> and clock <= <time_to>` 로 읽는다.
6. 아이템마다 머리 줄 + 값 줄 + 빈 줄을 이어 붙인다.
7. 파일 이름: `'data_'.$csvType.'_'.date("YmdHis").'.csv'`.

**판정 기준**

- **history / trends 구분**:
  ```php
  $timeRange = $jsonTime['time_to'] - $jsonTime['time_from']; // 검색 시간 범위 timestamp 값
  $rangeValue = 3600 * 2; // trends 데이터 검색으로 변경될 범위 조건 (3600 = 1시간)
  ...
  if ($timeRange < $rangeValue) {
  ```
  기간이 **2시간 미만**이면 history, **2시간 이상**이면 trends.
- **표 고르기**: `value_type == 3` 이면 `history_uint` / `trends_uint`, 아니면 `history` / `trends`.
- **CSV 열**:
  - history: `"HOST","ITEM","수집시간","값(value)"`
  - trends: `"HOST","ITEM","집계시간","최소","평균","최대"`
  - 시각 모양: `date("Y-m-d H:i:s", clock)`.
- **호스트·아이템 찾기**: `IN (...)` 완전 일치. 호스트는 기술 이름(`h.host`), 아이템은 이름(`i.name`).
- **기간 조건**: 양쪽 포함(`>=`, `<=`).
- **글자 인코딩**: EUC-KR 로 바꾸는 줄은 주석이다. 그대로(UTF-8) 내보낸다.
- **권한**: 일반 사용자 이상. `hostid` 를 넘기면 그 호스트를 볼 수 있는지 API 로 확인한다.

## 3.10 장기 미접속 계정 현황

**화면** (5버전 화면에서 확인)

- 액션: `user.unconnect`.
- 메뉴 위치: 관리 > 장기 미접속 계정 현황 (`유저` 바로 다음).
- 제목: `장기 미접속 계정 현황`.
- 오른쪽 위: `유저 그룹` 선택 상자(기본 `모두`).
- 필터(한 줄): 로그인 이름, 이름, 성, 유저 종류(`전부` / `Zabbix User` / `Zabbix Admin` / `Zabbix Super Admin`). 버튼 `적용`, `리셋`.
- 표의 열: 로그인 이름(정렬 표시) / 이름 / 성 / 유저 종류 / 그룹 / 최근접속일시.
- 값 모양: 그룹은 유저 그룹 이름을 `, ` 로 이은 것. 최근접속일시는 `YYYY/MM/DD HH:MM:SS`, 기록이 없으면 빈칸. 로그인 이름은 링크.
- 표 아래: `N 중 N건을 표시하고 있습니다`. 대상이 없으면 `데이터를 찾을 수 없음`.
- 버튼·팝업: 없다.

**데이터 출처**

| 무엇 | 어디서 |
|---|---|
| 대상 사용자 id | `users`, `sessions`, `auditlog` 를 SQL 로 직접 읽음 |
| 사용자 정보 | `API::User()->get()` (`userid, alias, name, surname, type, autologout, attempt_failed`, 그룹 `name, gui_access, users_status`) |
| 유저 그룹 목록 | `API::UserGroup()->get(['output' => ['name'], 'preservekeys' => true])` |
| 최근 접속 시각 | `sessions` 의 `MAX(lastaccess)` |
| 필터 값 | 프로파일 `web.user.filter.usrgrpid`, `web.user.filter_alias`, `web.user.filter_name`, `web.user.filter_surname`, `web.user.filter_type` |

**조회 방법**

1. 유저 그룹, 정렬, 필터를 프로파일에 저장하고 읽는다.
2. 대상 사용자 id 를 구한다.
   ```sql
   select userid from users
   where userid not in (select userid from sessions
                        GROUP BY userid
                        having max(lastaccess) > extract(epoch from now() - interval '60 day')::int )
     and userid !=1
     and alias in (select resourcename from auditlog A
                   where action ='0'
                   and resourcetype =0
                   and clock < extract(epoch from now() - interval '60 day')::int)
   ```
   (원문은 PHP 문자열을 `.` 으로 이어 붙인 것이다. 줄바꿈만 정리했다.)
3. 그 id 목록을 `'userids'` 에 넣고, 필터를 `'search'`(alias, name, surname), `'filter'`(type), `'usrgrpids'` 로 넣어 `API::User()->get()` 을 부른다. `'limit' => $config['search_limit'] + 1`.
4. `CArrayHelper::sort()` 로 정렬하고 `CPagerHelper::paginate()` 로 페이지를 나눈다.
5. 화면에 나올 사용자들의 최근 접속을 읽는다: `SELECT s.userid,MAX(s.lastaccess) AS lastaccess,s.status FROM sessions s WHERE <userid 조건> GROUP BY s.userid,s.status`. 사용자마다 가장 큰 값을 남긴다.
6. 뷰가 표를 그린다.

**판정 기준**

- **장기 미접속** = 아래 세 가지를 모두 만족하는 사용자.
  1. 최근 60일 안에 접속 기록(`sessions.lastaccess`)이 있는 사용자가 **아니다**. 세션 기록이 아예 없는 사용자도 여기에 든다.
  2. `userid` 가 1 이 아니다.
  3. 로그인 이름이 `auditlog` 에서 `action ='0'`, `resourcetype =0`, **60일보다 전**(`clock <`)인 기록의 `resourcename` 에 있다.
- **기준 일수**: 60일. SQL 에 `interval '60 day'` 로 두 번 박혀 있다. 설정 화면은 없다.
- **비교**: 접속은 `max(lastaccess) > 60일 전` 이면 제외. 감사 기록은 `clock < 60일 전`.
- **3번의 숫자 뜻**: 소스에는 숫자만 있고 상수 이름이 없다. Zabbix 5.0 기본 상수로는 `action` 0 이 "추가", `resourcetype` 0 이 "사용자"다. 그렇다면 3번은 "만든 지 60일이 넘은 계정"이라는 뜻이 된다. 이 풀이는 소스에서 직접 확인한 것이 아니다.
- **최근접속일시 색**: 세션이 살아 있고(`ZBX_SESSION_ACTIVE`), 그룹이 사용 중이고, `lastaccess + 온라인 인정 시간 >= 지금` 이면 초록, 아니면 빨강. 기록이 없으면 빈칸(빨강 클래스).
- **그룹 칸**: `max_in_table` 개까지만 보이고 넘으면 `…`.
- **정렬**: 허용 값 `alias, name, surname, type`. 기본 `alias` 오름차순.
- **권한**: 최고 관리자(`USER_TYPE_SUPER_ADMIN`)만.

**근거**

| 간편인증 결과 확인(서버) | `CWebUser::fidoCertResult(name, password, cid)` |
| 간편인증 결과 확인(브라우저) | `mpass_result.php` 에 POST (`uid`, `password`, `cid`) |
| OTP 기록 | 파일 `/var/log/zabbix/log/OTP?YYYY-MM-DD.log` (`?` 자리는 한 글자를 읽지 못함) |

**조회 방법 — OTP 로그인**

1. 폼은 `action='index_hidfrm.php'`, `target='hidfrm'` 으로 만들어진다.
2. `index.php` 는 이 조건일 때 로그인시킨다.
   ```php
   if (hasRequest('enter') && getRequest('mpass','')!='1' && CWebUser::OTPCheck(getRequest('name', ZBX_GUEST_USER), getRequest('password', ''), getRequest('otp',''))) {
   ```
   기본 Zabbix 의 `CWebUser::login(...)` 줄은 바로 위에 주석으로 남아 있다.
3. 성공하면 기본과 같이 `autologin` 을 갱신하고 이동한다.

**조회 방법 — 간편인증**

1. 사용자가 간편인증 상자를 체크하면 `index.php` 의 스크립트가 OTP 입력란을 비우고 `readonly` 로 만든다.
2. 폼이 숨은 `iframe`(`hidfrm`) 안의 `index_hidfrm.php` 로 전송된다.
3. `index_hidfrm.php`: `mtype` 이 `C` 이면 `C`, 아니면 `A` 로 정한다. `enter` 가 있고 `mpass` 가 `1` 이면 `CWebUser::fidoCertReq(...)` 를 부른다. 결과 글자를 `:` 로 나눈다(`[0]` = 결과 코드, `[1]` = 요청 id).
4. `mtype` 이 `A` 이고 결과 코드가 1 이면, 부모 창에서 로그인 영역을 숨기고 대기 창을 띄우고 `cid` 에 요청 id 를 넣는다.
5. 1초마다 남은 시간을 갱신한다. **5초마다** `mpass_result.php` 에 POST 한다.
6. 응답이 `"true"` 이면 부모 폼의 `mtype` 을 `R` 로, `action` 을 `index.php`, `target` 을 `_self` 로 바꾸고 `enter` 를 누른다.
7. `index.php` 는 이 조건일 때 로그인시킨다.
   ```php
   if (getRequest('mpass')=='1'  && getRequest('mtype')=='R' && CWebUser::fidoCertResult(getRequest('name', ZBX_GUEST_USER), getRequest('password', ''), getRequest('cid',''))) {
   ```
8. 30초가 되면 타이머를 멈추고 `mtype` 을 `C` 로 바꿔 `index_hidfrm.php` 로 다시 보낸다(취소 요청). 응답 쪽은 부모 창을 새로 고친다.
9. 4번에서 결과 코드가 1 이 아니면 실패 알림창을 띄우고 부모 창을 새로 고친다.

**판정 기준**

- **OTP 경로**: `enter` 있음 + `mpass` 가 `'1'` 이 아님 + `OTPCheck()` 참.
- **간편인증 경로**: `mpass == '1'` + `mtype == 'R'` + `fidoCertResult()` 참.
- **`mtype` 값**: `A` = 인증 요청, `R` = 결과 확인 후 로그인, `C` = 취소.
- **대기 시간**: 30초. 결과 확인 간격 5초(`cnt%5==0`).
- **요청 성공 판단**: `fidoCertReq()` 결과의 첫 조각이 1.
- OTP 번호와 간편인증을 실제로 어떻게 확인하는지(어느 서버에 무엇을 보내는지)는 **확인 못 함**. 그 함수들이 복원본에 없다.

**근거**

**확실하지 않은 것 / 없는 것**

## 3.13 일별 집계 배치 (batch.sql)

저사용 서버, CPU Top 10, Memory Top 10 이 읽는 별도 표 `extends_trends_day` 를 채우는 방법이다. 채우는 코드가 **세 군데**에 있고 서로 조금씩 다르다.

**화면**

화면은 없다. `batch.sql` 은 PostgreSQL 함수 `batch_trends_day()` 를 만들고, 파일 마지막 줄 `select batch_trends_day();` 로 바로 실행한다.

**데이터 출처**

| 무엇 | 어디서 |
|---|---|
| 원본 | `zabbix.trends` (시간별 `num, value_min, value_avg, value_max`). `trends_uint` 는 읽지 않는다 |
| 호스트·키·단위 | `zabbix.items` (`hostid, key_, units`) |
| 결과 | `extends_trends_day` |

`extends_trends_day` 의 열(`...CPU` 의 표 정의):

| 열 | 형 | 뜻 |
|---|---|---|
| `hostid` | int8 | 호스트 |
| `itemid` | int8 NOT NULL | 아이템 |
| `key_` | varchar(255) | 아이템 키 |
| `clock` | int4 | 그 줄의 기준 시각(넣는 코드마다 다름. 아래 표) |
| `weekend` | int4 | 요일 번호(`isodow`). `...Memory` 의 표 정의에는 이 열이 없다 |
| `clock_day` | varchar(255) | 날짜 글자 `YYYY-MM-DD` |
| `num` | int4 | 표본 수 합 |
| `value_min`, `value_avg`, `value_max` | float8 | 하루 전체 |
| `work_min`, `work_avg`, `work_max` | float8 | 업무시간 |
| `night_min`, `night_avg`, `night_max` | float8 | 업무외시간 |
| `units` | varchar(20) | 단위 |

**조회 방법 — batch.sql**

1. `truncate table extends_trends_day;` 로 표를 비운다.
2. 시작 시각을 정한다: `extends_trends_day` 의 `max(clock)`. 없으면 `trends` 의 `min(clock)`.
3. 끝 시각: `trends` 의 `max(clock)`.
4. `startclock <= 끝 시각` 인 동안 하루(86400초)씩 반복한다.
   1. 요일: `weekend := extract (isodow from to_timestamp(startclock));`
   2. 하루 전체를 넣는다.
      ```sql
      INSERT into extends_trends_day (itemid, num, value_min, value_avg, value_max, clock, weekend)
      SELECT itemid, sum(num) as num, min(value_min) as value_min, avg(value_avg) as value_avg, max(value_max) as value_max, endclock, weekend
      FROM zabbix.trends
      WHERE clock >= startclock
      and clock < (startclock + 86400)
      group by itemid;
      ```
   3. 업무시간 값을 갱신한다: `clock >= (startclock + 9 * 60 * 60) and clock < (startclock + 18 * 60 * 60-1)`.
   4. 업무외시간 값을 갱신한다: `(clock >= startclock and clock < (startclock + 9 * 60 * 60 -1)) or (clock >= (startclock + 18 * 60 * 60) and clock < (startclock + 86400 -1))`.
   5. `hostid` 가 비어 있는 줄에 `items` 의 `hostid, key_, units` 를 넣는다.
   6. `startclock := endclock;`
5. 반복 횟수를 돌려준다.

**조회 방법 — PHP 쪽 보충 코드**

- `...CPU::check()` → `batchDailyTrends()` : 조회 기간의 날짜를 하루씩 돌며 `clock_day` 로 줄이 있는지 보고, 없는 날짜의 INSERT + UPDATE 문을 **한 문자열에 모아** 마지막에 `DBselect($query)` 한 번으로 실행한다. 마지막에 요일을 갱신한다.
- `...Memory::check()` : 같은 방식이지만 날짜마다 바로 실행한다. 요일 갱신이 없다.
- 평균 계산 방식은 세 곳이 같다: 하루 전체 = `avg(value_avg)`, 최소 = `min(value_min)`, 최대 = `max(value_max)`. 업무시간·업무외시간도 같은 함수를 시간 조건만 바꿔 쓴다.

**판정 기준**

세 곳의 차이:

| 항목 | `batch.sql` | `...CPU::batchDailyTrends()` | `...Memory::check()` |
|---|---|---|---|
| 줄의 `clock` | `startclock + 86400` (구간의 끝) | 그날 `00:00:00` + 86399 (= 23:59:59) | 그날 `00:00:00` |
| `clock_day` | 넣지 않음 | 넣음 | 넣음 |
| `weekend` | 넣음 | 마지막에 갱신 | 넣지 않음 |
| 대상 아이템 | `trends` 의 모든 아이템 | CPU 키 3개 조건 | CPU 키 3개 조건 |
| 하루의 시작 | `trends` 의 가장 이른 `clock` 에서 86400초씩 | 날짜의 00:00:00 | 날짜의 00:00:00 |
| 하루 전체 | `[시작, 시작+86400)` | `[00:00:00, 23:59:59)` | 같음 |
| 업무시간 | `[시작+9시간, 시작+18시간−1초)` | `[09:00:00, 18:00:00)` | 같음 |
| 업무외시간 | `[시작, 시작+9시간−1초)` 와 `[시작+18시간, 시작+86400−1초)` | `[00:00:00, 09:00:00)` 과 `[18:00:00, 23:59:59)` | 같음 |
| 불리는 곳 | 확인 못 함 | 복원본에는 부르는 곳이 없다(`process()` 안의 호출이 주석) | `...Memory::process()` (Memory Top 10) |

읽는 쪽 조건은 항상 `clock >= 시작일 00:00:00` 그리고 `clock < 종료일 23:59:59` 다. 그래서 줄의 `clock` 을 넣은 방식에 따라 결과가 달라진다(코드를 그대로 따라간 결과).

| 줄의 `clock` | 기간 "D1 ~ D2" 로 읽을 때 |
|---|---|
| 그날 23:59:59 (`...CPU` 방식) | D2 의 줄은 `clock < D2 23:59:59` 에 걸려 빠진다 |
| 구간의 끝 (`batch.sql` 방식, 시작이 자정일 때) | 날짜 X 의 줄이 X+1 00:00:00 으로 들어가 있어, D1−1 ~ D2−1 의 줄이 잡힌다 |
| 그날 00:00:00 (`...Memory` 방식) | D1 ~ D2 의 줄이 잡힌다 |

운영 환경의 표가 어느 방식으로 채워졌는지는 확인 못 함.

**근거**

- `batch.sql:1-88` (비우기 `:13`, 시작 `:16-25`, 끝 `:28-30`, 반복 `:33-82`, 요일 `:40`, 전체 `:45-51`, 업무시간 `:54-61`, 업무외 `:64-71`, 호스트·키 `:74-78`, 실행 `:88`)
- 표 정의: `...CPU.php:432-455`, `...Memory.php:198-221`
- `...CPU` 보충: `...CPU.php:63-89`, `:92-176` (clock `:107`, 키 `:110-114`, 전체 `:117-125`, 업무시간 `:131-136`, 업무외 `:141-148`, 요일 `:169-172`, 실행 `:174`)
- `...Memory` 보충: `...Memory.php:67-161` (clock `:104`, 키 `:107-111`, 실행 `:144`)
- 호출 주석: `...CPU.php:205`. 호출: `...Memory.php:166`
- 읽는 조건: `...CPU.php:240-241`, `...Memory.php:176-177`, 기간 변환 `...CPU.php:30-43`

**확실하지 않은 것 / 없는 것**

- `batch.sql` 을 **언제, 무엇이 실행하는지**(예약 작업인지 손으로 돌리는지) 확인 못 함. routing.php 에 `popup.batch` / `CControllerPopupBatch` 가 있으나 내용이 없고, 이 SQL 과의 관계도 확인 못 함.
- `batch.sql` 이라는 파일 이름은 흐리게 읽은 것이다. 56번째 줄의 구두점 하나(`,` 또는 `.`)를 읽지 못했다.
- `...CPU` 에는 월 단위 표 `extends_trends__month`(밑줄 2개), `extend_trends_month` 의 정의와 `checkMonth()`, `trendHour()`, `trendDay()`, `trendMonth()`, `trendsData()` 가 있다. 함수 머리 줄들이 빠져 있고, 복원본에서 이 함수들을 부르는 곳은 찾지 못했다.
- 프로젝트 목록에 `lowserver.sql` 이라는 이름이 있었으나 내용이 없다.
- `...Data` 의 `queryWhereLikeOr()` 가 없어, PHP 보충 코드의 키 조건이 정확히 어떤 SQL 이 되는지 확인 못 함.

**알려진 문제**

- **실행할 때마다 처음부터 다시 만든다.** 첫 줄이 `truncate` 다. 그래서 2번의 "이어서 하기" 갈래(`시작위치2`)는 탈 수 없다. `trends` 보관 기간 전체를 하루씩 다시 훑는다 (`batch.sql:13-25`).
- **하루의 시작이 자정으로 맞춰지지 않는다.** 시작점이 `trends` 의 가장 이른 `clock` 이다. 그 시각이 자정이 아니면 "하루", "09~18시"가 모두 그만큼 밀린다 (`batch.sql:20`, `:33`, `:57-58`).
- **`clock_day` 를 넣지 않는다.** `...Memory::check()` 는 `clock_day` 로 "그 날짜 줄이 있는지"를 본다. `batch.sql` 로 채운 줄은 날짜가 없어 "없음"으로 보이고, 같은 날짜를 다시 INSERT 하게 된다 (`batch.sql:46`, `...Memory.php:83-85`, `:99`).
- **PHP 보충 코드의 INSERT 가 `trends` 에 없는 열을 조건으로 쓴다.** `FROM zabbix.trends ... and <key_ 조건>` 인데, 기본 Zabbix 의 `trends` 표에는 `key_` 열이 없다(`queryWhereLikeOr()` 가 `key_` 조건을 만든다는 것은 `CDataItems` 의 같은 이름 함수와 `...CPU.php:251` 의 글자로 미루어 본 것이다) (`...CPU.php:120-123`, `...Memory.php:116-119`).
- **Memory 보충 코드가 CPU 키로 거른다** (`...Memory.php:107-111`).
- **업무시간 최대값 열을 읽는 쪽에서 쓰지 않는다.** 표에는 `work_max` 가 있지만 읽는 쿼리는 `max(value_max) as work_max` 다 (`...CPU.php:237`, `:265`, `...Memory.php:173`).
- **표 이름에 스키마가 붙었다 안 붙었다 한다.** `extends_trends_day`, `trends` 와 `zabbix.trends`, `zabbix.items` 가 섞여 있다 (`batch.sql:13`, `:20`, `:48`, `:76`).
- **인덱스·기본 키 정의가 없다** (`...CPU.php:434-454`).
- **화면을 여는 요청 안에서 표를 만들고 채운다**(`...Memory` 쪽). 빠진 날짜가 많으면 그만큼 INSERT/UPDATE 가 실행된다 (`...Memory.php:72-74`, `:95-148`).

| `...Data` (trait) | 거의 모든 커스텀 컨트롤러, `...CPU`, `...Memory` | SW 인벤토리, 저사용, 일일점검, 윈도우즈, Top 10 | `queryWhereOr()`, `queryWhereLikeOr()` 의 정확한 SQL, 선언되지 않은 속성이 여기 있는지 |
| `...WindowsAll` (trait) | `CControllerWindowsAll` | 윈도우 전체 | 열 함수와 가운데 처리 |

| `CWebUser` 의 `OTPCheck()`, `fidoCertReq()`, `fidoCertResult()` | `index.php`, `index_hidfrm.php` | 로그인 | 인증 서버와 주고받는 내용 전체 |
| `host_ipAddress()` | `...Inventoris` | SW 인벤토리 | 정의 위치 |

`order_result()`, `validateTimeSelectorPeriod()`(전역 함수 모양의 호출)도 복원본에 정의가 없다. Zabbix 기본 함수인지는 복원본만으로는 확인 못 함.

### 4.7 화면별로 본 영향

| 화면 | 소스만으로 다시 만들 수 있는 정도 |
|---|---|
| 장기 미접속 계정 현황 | 컨트롤러와 뷰가 모두 있다. 그대로 따라갈 수 있다 |
| 일일점검 | 계산 방법은 모두 있다. 줄 정의(`daily.json`)와 뷰는 화면 설명으로 채워야 한다 |
| 저사용 서버 | 판정식과 조회는 있다. 규칙 파일, 뷰, CSV, 기준설정 저장이 없다 |
| 윈도우즈 패치 현황 | 목록과 팝업은 있다. 규칙 파일, 뷰, CSV 가 없다 |
| 서버 시간 확인 | 조회는 있다. 값을 화면 글자로 바꾸는 뷰가 없다 |
| SW 인벤토리 | 조회와 Agent 판정은 있다. 마스크 적용 이후와 뷰, CSV, Agent 입력 팝업이 없다 |
| 성능 데이터 추세 분석 | CSV 는 있다. 화면 동작을 맡는 JS 가 없다 |
| CPU/Mem 사용률 추출 | 뷰는 있다. 읽는 표의 정의와 채우는 방법, 셸 스크립트가 없다 |
| 고사용 서버 | 규칙 파일과 화면 설명만 있다. 판정식을 소스로 확인할 수 없다 |
| Box 사용현황 | 열 함수와 규칙 파일만 있다 (옮기지 않기로 함) |
| 로그인 | 흐름은 있다. 실제 인증 함수가 없다 |
| Peak 이벤트 분석 | 화면 설명만 있다 |
