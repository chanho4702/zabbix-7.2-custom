# 서버 시간 확인 (`uptime.list`)

## 1. 한눈에

| 항목 | 내용 |
|---|---|
| 메뉴 위치 | 보고서 > 서버 시간 확인 (코어 보고서 메뉴 뒤에 붙는 모듈 메뉴 중 첫 번째. `Module.php` 의 `REPORT_MENUS`) |
| 주소 | `zabbix.php?action=uptime.list` |
| 상태 | **완성** (2026-11-23 구현). 설정 없이 동작한다. 5버전 뷰 파일을 받지 못해 Description 출처만 가정이다 (7장) |
| 5버전 액션 | `uptime.view` (컨트롤러 `CControllerUptimeView.php`, 부모 `CControllerUptime.php` 의 `prepareData()`) |
| 내보내기 | 없음 (5버전 컨트롤러에도 내보내기 처리가 없었다) |
| 권한 | 로그인한 사용자 중 게스트가 아닌 사람(`getUserType() >= USER_TYPE_ZABBIX_USER` 이고 `!CWebUser::isGuest()`). 표에 나오는 호스트는 API 가 사용자 권한으로 거른다. 5버전도 User 이상이었다 |

## 2. 이 화면은 무엇을 하나

서버별로 "지금 몇 일째 켜져 있는지(가동 시간)"와 "언제 부팅했는지"를 한 표로 보여 주는 화면이다.
운영 담당자는 오래 재부팅하지 않은 서버(예: 180일 이상)를 골라 패치/재부팅 계획을 세우거나, 예상하지 못한 재부팅이 있었는지 확인하는 데 쓴다.
필터의 "서버 Uptime N day 이상"으로 오래 켜져 있는 서버만 골라 볼 수 있다.
(화면 이름이 "서버 시간"이라 서버 시계가 맞는지 보는 화면으로 오해하기 쉽지만, "서버 Time" 열은 시계가 아니라 가동 시간이다. 5버전 소스에서 확인했다)

## 3. 화면 구성

### 필터

| 이름 (한국어 화면) | 입력 방식 | 기본값 | 저장 여부 |
|---|---|---|---|
| 호스트 그룹 | 선택창(멀티셀렉트) + [선택] 팝업. 하위 그룹 포함 | 비어 있음(전체) | 저장 (`web.dmove.uptime.filter.groupids`) |
| 호스트 | 선택창(멀티셀렉트) + [선택] 팝업 | 비어 있음(전체) | 저장 (`...filter.hostids`) |
| OS/Version | 텍스트. 인벤토리 `os` 필드를 대소문자 무시 부분 일치로 찾는다 | 빈 값 | 저장 (`...filter.os`) |
| 서버 Uptime | 텍스트(숫자), 흐린 안내 글자 "day 이상" | 빈 값 | 저장 (`...filter.uptime_days`). 숫자가 아니면 빈 값으로 저장 |

### 표의 열

| 열 | 값의 출처 | 표시 방식 |
|---|---|---|
| 호스트 | 호스트 표시 이름 | 줄바꿈 안 함. 제목을 누르면 정렬 |
| IP | 대표 IP (`HostHelper::mainIp()`) | 줄바꿈 안 함 |
| Description | ITSM 설명, 없으면 Zabbix 호스트 설명 (가정. 7장) | 긴 글은 줄바꿈 |
| OS | 호스트 인벤토리의 `os` 필드. 인벤토리가 꺼져 있으면 빈칸 | 글자 그대로 |
| 서버 Time | 아이템 `system.uptime` 의 마지막 값(초)을 `158 일, 13:38:45` 형식으로 | 줄바꿈 안 함. 제목을 누르면 가동 시간으로 정렬. 값이 없으면 `-` |
| 서버 start | 값을 수집한 시각 - 가동 초 = 부팅 시각. `2026/06/18 07:33:24` 형식 | 줄바꿈 안 함. 값이 없으면 `-` |

`system.uptime` 아이템이 있는 호스트만 나온다. 표 아래에 페이지 이동이 있다.

## 4. 어떻게 만들었나 (동작 순서)

1. **CSRF 검사 끄기** - `UptimeList::init()` 에서 `disableCsrfValidation()`.
2. **입력 검증** - `UptimeList::checkInput()`
   `page`, `sort`(`host`, `uptime`), `sortorder`, `filter_set`, `filter_rst`, `filter_os`(문자열), `filter_uptime_days`(문자열) + `HostFilter::INPUT_FIELDS`(`filter_groupids`, `filter_hostids` = 숫자 ID 배열).
   일수를 문자열로 받는 이유: 빈 칸으로도 넘어오기 때문이다. 숫자 검사는 다음 단계에서 한다.
3. **권한** - `UptimeList::checkPermissions()`: `getUserType() >= USER_TYPE_ZABBIX_USER && !CWebUser::isGuest()` (게스트 계정 제외).
4. **필터 저장/초기화** - `UptimeList::doAction()` 1번 블록
   - [적용]: `HostFilter::save()` 로 그룹/호스트 ID 배열을 저장, OS 와 일수는 `CProfile::update()`.
   - 일수는 `normalizeDays()` 를 거친다. `ctype_digit()` 로 0~9 로만 된 글자인지 본다. 예) `"30"` -> `"30"`, `"30일"` -> `""`, `"-5"` -> `""`.
   - [리셋]: `HostFilter::reset()` 과 `CProfile::deleteIdx()`.
5. **필터와 정렬 값 읽기** - `HostFilter::load()`, `CProfile::get()`. 정렬 값은 주소에 없으면 지난번 값을 쓰고 다시 저장한다 (`web.dmove.uptime.sort`, `...sortorder`).
6. **데이터 조회** - `UptimeList::getRows()`
   1. 호스트를 한 번에 읽는다.
      ```php
      $options = HostFilter::toApiOptions($host_filter) + [
          'output' => ['hostid', 'name', 'description'],
          'with_monitored_items' => true,           // 모니터링 중인 아이템이 있는 호스트만 (5버전과 같다)
          'selectInventory' => ['os'],
          'selectInterfaces' => HostHelper::INTERFACE_FIELDS,
          'preservekeys' => true
      ];
      if ($filter['os'] !== '') {
          $options['searchInventory'] = ['os' => $filter['os']];   // 인벤토리 os 부분 일치
      }
      ```
   2. 그 호스트들의 가동 시간 아이템을 **한 번에** 읽는다.
      ```php
      API::Item()->get([
          'output' => ['itemid', 'hostid', 'lastvalue', 'lastclock'],
          'hostids' => array_keys($hosts),
          'filter' => ['key_' => 'system.uptime', 'status' => ITEM_STATUS_ACTIVE]
      ]);
      ```
      - `lastvalue` = 마지막 수집 값(가동 초), `lastclock` = 그 값을 수집한 시각. 수집된 적이 없으면 `lastclock` 이 0 이다.
   3. ITSM 설명 표를 읽는다 (`ItsmRepository::fetchDescriptions()`).
   4. 아이템마다 행을 만든다. 예) `lastvalue` = 13,700,325초
      - 서버 Time: `formatUptime()`. 13,700,325 / 86,400 = 158일, 나머지 49,125초 = 13:38:45 → `158 일, 13:38:45`.
        나머지 초는 `gmdate('H:i:s', ...)` 로 바꾼다. `date()` 를 쓰면 시간대 9시간이 더해져 틀린다.
      - 서버 start: `date('Y/m/d H:i:s', lastclock - lastvalue)`. 사용자 시간대로 표시된다.
      - "N day 이상" 필터: `intdiv(가동 초, 86400) < N` 이면 뺀다. 필터를 걸었는데 값이 없는 호스트도 뺀다.
7. **정렬** - `sortRows()`. 가동 시간은 숫자로 비교하고, 값이 없는 호스트는 방향과 관계없이 맨 뒤에 둔다. 값이 같으면 호스트 이름 순.
8. **페이징** - `CPagerHelper::paginate(..., ZBX_SORT_UP, ...)`. 이미 정렬한 전체 목록이라 세 번째 인자는 항상 `ZBX_SORT_UP` 이다.
9. **화면** - `views/reports/uptime.list.php`
   `HostFilter::addRows()` 로 그룹/호스트 두 줄을 만들고 OS, Uptime 입력을 붙인다. 호스트와 서버 Time 제목은 `make_sorting_header()` 로 정렬 링크가 된다.

## 5. 5버전과 비교

| 주제 | 5버전 | 7버전 | 왜 |
|---|---|---|---|
| 필터 구성 | 호스트 그룹, 호스트, OS/Version, 서버 Uptime("day 이상") | 같다 | 그대로 옮김 |
| 표 구성 | 호스트, IP, Description, OS, 서버 Time, 서버 start | 같다 | 그대로 옮김 |
| 컨트롤러 구조 | 코어 "최근 데이터" 화면 컨트롤러를 복사해서 고친 것. 쓰지 않는 코드(애플리케이션 조회, 매크로 풀기, 상세 보기 옵션)가 많이 남아 있었다 | 이 화면에 필요한 조회만 | 7버전에는 애플리케이션이 없다. 읽기 쉽게 |
| 가동 시간 아이템 | 키 `system.uptime`, 사용 중인 아이템 | 같다 | 그대로 옮김 |
| 호스트 조회 | `with_monitored_items`, 인벤토리 `os` 부분 일치(`searchInventory`), "검색/필터 결과 제한"(기본 1000) + 1 개까지만 | 같은 조건. 개수 제한 없이 필터에 맞는 호스트를 모두 읽는다 | 1000대가 넘어도 뒤쪽이 잘리지 않게 |
| 마지막 값 | 코어 이력 관리자로 최근 값 2건 (최근 24시간 범위) | `item.get` 의 `lastvalue` / `lastclock` (같은 24시간 범위) | 결과 같음. 호출이 단순하다 |
| "N day 이상" 계산 | 아이템마다 SQL 을 한 번씩 실행해 날짜 차이(`date_part('day', ...)`)를 구했다 | PHP 에서 `intdiv(가동 초, 86400)` | 결과 같음. 호스트 수만큼 쿼리를 하지 않는다 |
| "N day 이상" 이 적용되는 때 | "데이터 없는 아이템 표시" 옵션이 꺼져 있을 때만 걸렀다. 그 옵션의 기본값은 켜짐이었다 (화면에 이 옵션이 보였는지는 뷰를 받지 못해 미확인) | 일수를 넣으면 항상 거른다 | 입력한 조건이 그대로 적용되게 |
| 값이 없는 호스트 | 기본은 표시 | 표시(`-`). 일수 필터를 걸면 뺀다 | 위와 같다 |
| IP | 인터페이스를 Agent > SNMP > JMX > IPMI 순으로 골라 IP 또는 DNS | `HostHelper::mainIp()` (Agent 기본 인터페이스 우선) | 공용 부품 사용 |
| 정렬 | `host`, `name`, `lastclock`, `lastvalue` | `host`, `uptime`(= 마지막 값) | 화면에 필요한 두 가지만 |
| 일수 입력 검사 | 문자열 그대로 비교 | 숫자만 저장, 아니면 필터 없음 | 잘못된 값으로 오류가 나지 않게 |
| 권한 | User 이상 | User 이상, 게스트 제외 | 게스트 차단 |
| 메뉴 | 보고서 아래 | 보고서 아래 (모듈 메뉴 중 첫 번째) | 5버전 순서 유지 |

## 8. 개선점

### 이미 반영한 개선

- 5버전 조건 그대로 조회 구현 (2026-11-23).
- 아이템마다 실행하던 날짜 계산 SQL 제거, 호스트 개수 제한 제거.
- 가동 시간 정렬(숫자 비교, 값 없는 호스트는 맨 뒤).
- 일수 입력값 검사, 사용자별 필터 저장, 호스트 그룹 선택 시 하위 그룹 포함.

### 남은 개선 제안

| 제안 | 효과 | 5버전과 결과가 달라지나 (고객 합의) |
|---|---|---|
| 표준 템플릿의 `system.localtime` 시각 차이 트리거(`fuzzytime()`)를 켜서 실시간 알람 병행 | 시계가 틀어진 서버를 화면을 열지 않아도 바로 알 수 있다 | 화면 결과와는 별개. 알람이 새로 생기므로 운영 합의 필요 |
| "시각 차이(초)" 열 추가 (`system.localtime` 값 - 수집 시각) | 이름 그대로 "서버 시간 확인"도 할 수 있다 | 열이 하나 늘어난다. 합의 권장 |
| 24시간 넘게 수집이 끊긴 서버도 마지막 값을 보여 주기 (`history.get` 으로 보완) | `-` 대신 마지막으로 알려진 값을 본다 | 5버전에 없던 표시. 합의 권장 |
| 내보내기(CSV/Excel) 추가 | 재부팅 계획 자료로 바로 쓴다 | 기능 추가 |

## 9. 확인 방법

### 테스트 환경 (http://127.0.0.1:18970, `Admin` / `zabbix`, `dev/compose.yaml`)

2026-11-23 에 아래 순서로 확인했다.

1. 시험 호스트 3대를 만든다. 각각 인벤토리를 켜고 `os` 에 `Red Hat Enterprise 7.9`, `Windows Server 2019`, `Rocky Linux 9` 를 넣는다. 에이전트 인터페이스에 IP 를 하나씩 준다.
2. 각 호스트에 아이템을 만든다: 키 `system.uptime`, 유형 Zabbix trapper, 정보 유형 숫자(부호 없는 정수).
3. 앞의 두 호스트에만 값을 넣는다 (세 번째는 값 없음).
   ```sql
   INSERT INTO history_uint (itemid, clock, value, ns)
   VALUES (<아이템1>, extract(epoch from now())::int - 60, 13700325, 0),
          (<아이템2>, extract(epoch from now())::int - 60, 3600, 0);
   ```
4. 보고서 > 서버 시간 확인을 연다 (`zabbix.php?action=uptime.list`).

| 조작 | 기대 결과 |
|---|---|
| 필터 없음 | 3줄. 첫째 `158 일, 13:38:45`, 둘째 `0 일, 01:00:00`, 셋째 `-` / `-` |
| 서버 Time 제목을 눌러 내림차순 | 158일 → 0일 → `-` 순서 (값 없는 호스트는 맨 뒤) |
| 서버 Uptime 에 `100` 넣고 [적용] | 첫째 호스트 1줄만 |
| OS/Version 에 `windows` 넣고 [적용] | 둘째 호스트 1줄만 |
| 서버 Uptime 에 `abc` 넣고 [적용] | 오류 없이 다시 열리고 칸이 빈 값이 된다 |

끝나면 시험 호스트와 그룹을 지운다.

### 고객환경에서 5버전과 비교

1. 같은 호스트 그룹으로 5버전 `uptime.view` 와 7버전 화면을 같은 시각에 연다.
2. 서버 start 가 몇 초 이내로 같으면 출처가 같다고 본다.
3. Uptime 필터(예: 100)를 같게 넣고 행 수를 비교한다. 5버전은 옵션에 따라 일수 필터가 적용되지 않을 수 있었으므로(5장), 7버전이 더 적게 나오면 그 차이인지 먼저 본다.
4. Description 이 다르면 5버전이 Zabbix 호스트 설명을 그대로 쓴 것이다. 7장의 가정을 고친다.
